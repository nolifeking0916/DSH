# 上下文注入以本地插件为单一来源

DSH 每轮对话的上下文供给，收敛为一条通道：`@local/context-inject` 独占供给「经验 + 技能 + 记忆」，每轮只发一条注入消息，每类内容各设一份配额；历史上的 `memos-autoinject` 与 `wikiskill-inject` 停用但不卸载，源码留在仓库、一行 profile 配置即可回滚。

不保留多路注入，是因为插件块每轮是**新增消息**（会累积），三路并跑实测每轮 1,966 字符、条目级重复 26.2%，且 MemOS 请求从 2 次涨到 4 次、串行多耗 0.6–0.8 秒；重复内容不只是浪费，还会让同一条经验在上下文里出现两次而降低权重感。

不把技能完全交给内核的技能目录，是因为这里有两条不同的轴：内核目录是「完整 + 稳定」（76 条 / 20,099 字符，每条描述上限默认 500），模型真正需要的是「相关 + 易变」的排序。两轴只能留一条，所以内核目录保留完整性、插件保留相关性排序，插件不再复制全量目录。经验与历史记忆内核根本不提供，只能由插件供给。

代价是供给质量依赖两处外部状态：MemOS 云库与本地 `~/.dsh/wiki/patterns/`。MemOS 不可达时退化为「经验 + 本地技能兜底」，技能排序质量下降；本地 wiki 缺失则经验段为空。两者都做成 fail-open，不让注入失败影响主流程。

同一轮里还踩到一个必须记下来的坑：`agent/pre-step` 的 `step` 是**会话内累计**的，写死 `injectStep: 1` 会让注入条件退化成「会话的第一次 agent step」——第一轮之后静默失效，插件显示 active、日志一行都没有。判据因此改为「用户消息是否变化」，而不是步数。

不动内核的注入机制：内核块（技能目录、工作区指令、运行时上下文、时间上下文）只做对齐与裁剪，不改其生成逻辑。

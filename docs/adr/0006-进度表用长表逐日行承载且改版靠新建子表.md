# 进度表用长表逐日行承载，改版靠新建子表

《集团人力近期重点工作进度表》改版后是**单表长表**：一行 = 事项 × 分项 × 日期，进展内容与当日计划逐日一一对应。

新版落在**在线表格《集团人力近期重点工作进度表》的新工作表「重点工作进度 v2」**里，原「工作表1」原样保留作底稿；另在智能表格（甘特）那份里建同名子表作镜像，供甘特图、分组与筛选用——两份数据由同一份 `rows_v2.json` 生成。

之所以落在线表格：源表本体是在线表格，日常维护（今天 13:12 的更新）也都发生在它上面；智能表格那份是 10-21 的转录副本，已过期。在线表格虽有合并原语，但目标版式**一个合并都不用**——每行独立、维度值逐行重复。

之所以走长表而不是宽表：智能表格**没有合并单元格这个原语**（`wecom-cli smartsheet --doc` 全文零命中，而姊妹服务「在线表格」有完整 merge 资源），且一条记录是「字段→单值」的扁平 map、没有嵌套子结构。所以「把多天进展拼进一个单元格」不是可选项而是缺陷，任何「每天一一对应」诉求都只能靠**一天一行**兑现。宽表方案是列对列，天然对不齐，且周数一多字段数暴涨。

之所以新建子表而不是原地改造：智能表格的**字段列顺序等于字段添加顺序**且 API 无法改写，**视图类型创建后不可改**（只能删了重建）。旧子表的 12 列顺序是旧版式留下的，按新目标版式排列只能靠新建子表时按目标顺序加列。这条约束是硬的，不是偏好。

代价是事项级字段（模块、责任人、开始/完成时间）在每行重复——167 行里重复了 13 列，也因此放弃了「事项主表 + 进展日志表」用 `reference` 关联的更干净形态（能力上支持，随时可切）。换来的是：任何一天的任何一条事项，都能在同一行里同时看到「当天进展」和「当天计划」，而这正是这张表存在的理由。

# 施测人报告「同源同数」三处全兑现

维护者 2026-10-26 19:3x 定（票 #49）：施测人报告会出两份，而且已经不一样了 ——
**生成器**（`src/report_sections.py` → Word/PDF/独立 HTML）有封面页、总→分→总、判读话术与可信度，
而**成品内的施测人报告页**（`src/modules/report.js`）与**云上 `/hr/` 汇总台**仍是旧的四段平铺，
「第一项／第二项／第三项」还在，可信度与判读话术都没有。
裁定：**三处全部兑现** —— 生成器、`/hr/` 汇总台、离线单文件内的施测人报告页共用同一套内容块定义，
旧 4-tab 结构下线。

理由：三处不是三个产品，是**同一份报告的三种交付形态**。施测人在汇总台日常看的那一份，
与归档给 HR 的那份文档，不该是两回事 —— 否则「按汇总台的说法追问、按文档归档」会自相矛盾。
只升级其中两处同样不可接受：那会留下两套渲染器长期并存，今天的「同源」明天又分叉。
离线单文件件虽然只是无网应急备件（#31），但它一旦冻结就与云版越差越远，
最终变成没人敢用的历史件 —— 所以它也要跟上。

做法：块定义的单一事实源 = `src/report_sections.py` 的 `build_blocks()` 抽出的 `src/report_blocks.py`；
JS 侧同构实现由新增的 `src/verify_block_parity.py` 机器逐块校验（不靠人眼比对）。
判读话术的云端表 `public.report_narrative` 是唯一真源，离线单文件内联它的导出快照
（2026-10-26 实测 148 行全 `active`、快照与云端表内容指纹一致 md5 `2a3cadbe…`），
并加一道门兜住「云端改了、快照没重导」。

**代价（明写下来，将来有人问「为什么离线件要涨 72KB」）**：离线单文件件从 232,552 B 涨到约 305 KB
（判读快照 62,823 B ＋ 画像文案 9,696 B）。这是为「离线件与云版同源同数」付的钱，
不接受「离线件就少给点」这种妥协。

**已知未决（各有后继票，勿在本 ADR 里当已定）**：
判读匹配逻辑现有三份实现（Python `report_narrative.py` / 云函数 JS `matchNarrative` / 单文件 JS），
parity 门只管其中两份，第三份的覆盖方式由票 #78 第 7 步定；
`#76` 的「正文不得出现五档词」断言与 `overall` 5 条 profile 话术正文冲突，须限定扫描范围；
类目名的适用范围仍未定（票 #50）。

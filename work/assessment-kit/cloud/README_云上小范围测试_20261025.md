## 二、架构与两个关键机制（**踩过的坑，别再踩**）

```
候选人浏览器（静态托管，独立子域名）
   └─ POST /api/assessment  ──► 网关路由（路径透传）──► HTTP 云函数 assessment
                                                              │  持 service_role 的 API Key（只在函数环境变量里）
                                                              └─► CloudBase PG  public.responses
施测人 ── GET /api/assessment?code=… ──► 同一函数 ──► 结果行 ──► 粘进现有成品的「施测人入口」出报告
```

**坑 1：浏览器不能直连 PG 写库。**
CloudBase 的 PG HTTP 网关（PostgREST）连接带 `row_security = off`，于是**凡是开了 RLS 的表，
非 `BYPASSRLS` 角色一律写不进去**（报 `42501 "violates row-level security policy"`，
很容易被误读成「策略写错了」——其实是 RLS 被整体跳过）。只有 `service_role`（`rolbypassrls=true`）能写。
⇒ 所以必须有云函数中转，**API Key 只进函数环境变量，绝不进浏览器代码**。

**坑 2：候选人必须读不到结果。**
同理，`row_security = off` 意味着**光靠 RLS 挡不住直读**。因此对 `public.responses`：
`REVOKE ALL … FROM anon, authenticated` + 只留 `service_role` 授权。
实测：publishable key 直读 → **401 permission denied** ✓（守住「候选人拿不到自己的报告」这条口径）。

## 三、4–5 人小范围测试怎么做

1. **发链接**：把候选人作答页链接发给 4–5 个人（`https://assessment-test-uu-one-d4gc4ot78a702cb70.webapps.tcloudbase.com`）。
   建议**同时发一段话**：全程约 30–40 分钟（96+76+40 题）；页面自带 90 分钟倒计时，**到点只提示、不会自动交卷**，
   你可以继续答、也可以自己点交卷；结果不显示在你的屏幕上，结果由 HR 保管。
2. **每人一件事**：打开链接 → 填姓名与身份证 → 同意并开始 → 作答 → **自己点交卷**。
3. **判据（跑通的定义）**：
   - 候选人能打开页面、能作答、能交卷（无报错、完成页显示「已完成」）；
   - 施测人侧能查到这一份（`GET ?code=…` 有行）；
   - 库里的 `m1_raw` 长度 = **96**（`stored:96`）；
   - 施测人能出报告（把结果行粘进现有成品的施测人入口 → 出三模块报告 + 总报告）。
4. **失败怎么查**：函数日志（CloudBase 控制台 → 函数 `assessment` → 日志）；表里逐份看
   （`SELECT code, submitted_at, jsonb_array_length(m1_raw) FROM public.responses ORDER BY submitted_at DESC`）。
5. **结束后**：把这一轮的 4–5 份结果**导出**（`GET ?action=list` 或直接查表），
   跑一遍既有分析工具（`pilot/analyze.py --real` 吃 JSON）确认链路到分析也通；
   然后**清掉测试数据**（`DELETE FROM public.responses WHERE code IN (…)`，或整表清空后重来）。

## 四、还没做、正式上线前必须补的（**别把这版当上线版**）

1. **题库与判据仍在前端**（票 #38 未决）：候选人打开开发者工具能读到 96 题的锚点与判据。
   ⇒ 4–5 人自测无所谓；**任何真实候选人场景之前**必须改成「判据放服务端、云函数算分」。
2. **函数与网关目前无鉴权**（`auth=false`，任何人都能 POST/GET）。4–5 人自测可接受；
   正式上线前要加：施测人读取接口的鉴权（角色/口令）、提交频率限制、链接与 `code` 的随机性。
3. **API Key 已在函数环境变量里**（`assessment_service_role`）。**这枚 key 等于数据库全权**，
   正式上线前必须轮换并用新 key 重新部署；**任何时候都不要把它写进仓、页面或截图**。
4. **汇总台没有**（票 #33 雾里那张）：现在只有「逐份取回」；逐份 + 汇总都要，是维护者 12:3x 的裁定（D7），
   但汇总台属承载侧，还没做。
5. **口径说明块与五级梯**（票 #39 的两处成品改动）在同一批改动的路上，完成后要**重新发布静态托管**。
6. **限时**现在是「保留倒计时、到点只提示不自动交卷」（D3）；自助场景下是否保留这个钟，还没最终定。

## 二、三个方案逐个展开

### 方案 A：发文件（候选人把结果 JSON 作为文件发给施测人）

#### A.0 一句话定性

**唯一既有实现、天然适配现有红线、但要在告知卡上补一行"回传到哪儿、多久收"。** 主要风险不是技术，是**载体留存边界**（结果会先进施测人个人微信/邮箱）。

#### A.1 三个载体的可行性差异（微信 / 邮件 / 网盘）

| 载体 | 文件是否原样 | 留痕强度 | 留存边界 | 现场可行性 | 定性 |
|---|---|---|---|---|---|
| **微信**（个人号） | 原样 | 弱（只有聊天记录） | ⚠ **告知卡 §4 明确写「不得长期存放于群聊与个人微信」** | 最高（被试本来就在微信里） | 可用，但**必须配"回收即删消息"的动作** |
| **企微** | 原样 | 弱偏中（有文件区、可设自动清理） | 企业侧留存，需 HR 明确边界 | 高 | 可用，同上 |
| **邮件** | 原样 | **强**（送达时间、收件人、附件名都在，可对账） | 邮箱在 HR 侧，边界可控 | 中（需要手机有邮件 App 或现场用电脑） | **跨天/异步场景最优**，因为唯一自带送达留痕 |
| **网盘** | 原样 | 弱 | ✗ **第三方服务器上的副本不受本项目的留存规则管辖** | 差 | **不建议**：与「零外链、数据只留本机、不自动上传」的硬约束正面冲突 |

差异结论：**主路径用微信/企微（现场最顺），异步或需要留痕时用邮件；网盘一律不用。**

#### A.2 候选人完成页文案草稿【提案 · 待拍板】

结构按本票第 2 点建议的**三段式（怎么交 / 交给谁 / 多久收）**。
⚠ 约束：完成页**不得出现分数与等级**、**不得给具体地址/联系人**（`测评设计规范_20261024.md` §五 完成屏硬约束）、**不得写本页做不到的表述**（红线 7）。

> **现状（`copy.js:28`，本稿不改）**
> `sendBody: "把刚下载的文件发回给你收到测评的那位同事（微信 / 企微 / 邮件均可）。"`

> **提案 A 版 `sendBody`**
> ```
> ① 怎么交：点上面的「下载结果文件（JSON）」，把下载到的那个 .json 文件原样发出去。
>    不要截图、不要用「文件传输助手」以外的转发方式，也不要改文件内容。
> ② 交给谁：发给你收到测评的那位同事（微信 / 企微 / 邮件都可以）。
>    建议先把文件改名为 EQ-{测评编号}.json 再发，这样我们对账更快。
> ③ 多久收：交卷后请在 {当场所内即可，最迟 __ 前} 把文件交给施测人。
>    如果不方便当场交，请在 {当天 __ 前} 发给我们，我们会主动提醒你一次。
> ```
> `{测评编号}` 取完成页已显示的编号（`app.js:282` 已渲染），`__` 为待拍板时填的空位。

**配套的提案改动（本稿不落地，仅登记）：**

| 字段 | 现状 | 提案 | 备注 |
|---|---|---|---|
| `sendTitle` | 「回传给施测人」 | 不变 | — |
| `doneLead` | 见 §1.1 | 不变 | 已含"不在本页面显示" |
| 新增 `sendDead`（回收时限句） | 无 | 见上 ③ | 时限值待拍板 |
| `doneLead` 后是否加"清除本机数据"提醒 | 「回传后，本机仍保留作答记录；你可随时清除。」 | **建议保留**，并在 §六 SOP 里加"施测人当场提醒一次" | 清除入口已实现（`app.js:284` / `clearAll`） |

#### A.3 施测人现场话术草稿【提案 · 待拍板】

> 「这一页就做完了，**分数不在您手机上显示**，这是设计好的。
> 现在麻烦您点一下上面那个『下载结果文件』，手机里会多出一个叫 `核心人才系列测试_<您的名字>.json` 的文件。
> 麻烦您**把这个文件本身**发回给我——微信、企微、邮件都行——**不要截图**，截图我这边算不了分。
> 改不改名字都行，您报一下屏幕上那个测评编号 `EQ-……`，我按编号对账。
> 发完之后，您点一下『清除本机数据』把手机上的作答记录删掉更放心。

要点：**明确"要文件不要截图"**（唯一能挡住方案 B 混进来的话）、**给编号作为对账锚点**、**主动提示清本机数据**（对齐告知卡 §4 留存表"出结果后由候选人自行清除"）。

#### A.4 回收时限与责任人建议【提案 · 待拍板】

| 项 | 建议 | 依据 |
|---|---|---|

| 回收时限（最迟） | **当天 18:00 前**（当日批次结束前） | 留一个跨天的兜底，但不允许拖到第二天 |
| 催收次数 | 1 次（未按时收到则电话/消息提醒一次），**只催 1 次，不追第二遍** | 避免变成骚扰；也避免"等消息"变成无限期 |

#### A.5 隐私 / PIPL 影响

- **告知卡第 5 条（数据处理）已经覆盖了"要主动回传"**，所以"结果离开浏览器"这一步**原则上已经告知过**。
- 但**没有写"回传到哪儿、走哪条路、结果会落在什么载体上、多久收"** → 这正是本票第 4 点要衔接的地方。
- **载体清单（告知卡 §1）漏了一环**：现有清单有"候选人下载的结果 JSON"，但没有"**回传途中的临时载体**（施测人个人微信 / 企微 / 邮箱）"。A 方案必然经过它 → **建议 §1 载体清单新增一行**。
- **PIPL 第 17 条（告知应真实、准确、完整）**：见 `work/assessment-kit/research/限时口径与计时效应_20261024.md` 第 242-253 行的条款要点表（引用该笔记整理的 PIPL 全文来源）。回传方式属于"处理方式"，**首次定稿时写全 ≠ 变更**；同一笔记引 PIPL 第 14 条要点写明"处理目的/方式/种类变更应重新取得同意" ⇒ **建议在告知卡定稿时一次写全，比上线后再补划算**。
- **PIPL 第 24 条（自动化决策 / 透明度 / 说明权）**：**回传方式本身不构成自动化决策**，不因选 A/B/C 而改变这条判断；自动化决策的讨论点仍在"结果如何进入招聘评估"（限时口径笔记 §3 的判断）。→ **本材料未发现"回传方式"与第 24 条存在直接关联的仓内依据。**
- **ADR-0004**：A 不引入完整身份证号、也不引入前 6 位 → **不冲突**。但**文件名带姓名**（`app.js:413`），详见 §五 5.3 与 §六 6.2。

#### A.6 失败模式与兜底

| 失败模式 | 现象 | 兜底 |
|---|---|---|
| **候选人不会发 / 发不了** | 不会用聊天工具传文件、文件找不到 | 切 **C1**（施测人当场来取）；不在当场解决的就**记 `exclude_reason` 作废** |
| **发了截图** | 微信里截图粘贴 | 施测人当场拒收并当场重下（话术里已堵）；事后收到截图一律不采信、不进统计 |
| **改文件名了** | 改成 `1.json`、`新建文件.json` | 不影响：登记表以**文件内 `code`** 为准；`result_json` 列填**规范名**（§六 6.2），原名记进 `quality_note` |
| **交了两次** | 同一 `code` 两个文件 / 两个不同 `code` | 同一 `code` → 取**最后一次下载**；不同 `code` → 属两次独立作答（告知卡清单 §3.4 明写"同一候选人同一天多次作答得到不同编号"）→ 登记为两行，择一或全剔，写 `exclude_reason` |
| **发丢了 / 撤回** | 消息撤回、没送达 | 当场收回（主路径本就在现场）；跨天场景由试测负责人按 §A.4 催 1 次 |
| **文件坏了** | 传输截断、网盘解压改名 | 施测人打开校验 9 个字段（`tool/version/code/name/idLast4/date/m1/m2/m3`）——作业包 §三 已要求确认字段齐全；校验不过当场重发 |
| **发错人** | 发给同事或领导 | 施测人核对 `code` 与登记表不符 → 拒收、登记、当场重发 |
| **施测人忘了粘贴** | `openReport()` 空跑出"本地演示报告" | **SOP 硬性要求**：导报告前必须先粘贴 JSON 并核对 `code`；核对动作写进 `quality_note` |

#### A.7 成本（对被试的技术要求）

- 要求：会点"下载"、会在微信/企微/邮件里**发一个文件**。
- **不要求**：注册账号、装 App、用网盘、知道文件在哪、知道 JSON 是什么。
- 样本结构（作业包 §二：内部候选人应聘 HR/管理岗 30–50 份 + 在职员工 30 份，分层到专员/经理/总监）⇒ 绝大多数被试**会发文件**。但"会发文件"与"会发文件且不截图"是两件事，**话术必须写死后者**。

### 方案 B：发图（截图回传）

#### B.0 一句话定性

**在当前成品与现有红线 6 下拿不到数据 —— 不是"防篡改难"，是"被测根本没有可截图的结果"。**

#### B.1 候选人在 B 下能截到什么？

| 候选截图对象 | 能拿到什么 | 能不能用于计分 |
|---|---|---|
| 完成页截图 | 只有"请下载并回传"的引导 + 测评编号 | ✗ 无任何数据 |
| 文件管理器里那个 `.json` 文件的**条目**（文件名/大小/时间） | 文件名（含姓名）+ 大小 + 修改时间 | ✗ 无任何数据 |
| 用文本编辑器打开 JSON 后**截图** | 理论上是完整 JSON | △ 理论可行，但见 B.2 |
| 结果分数截图 | — | **候选人端根本不显示分数**（红线 6），**这个对象不存在** |

⇒ **B 要成立，候选人端必须能看见结果或结果文本 —— 而那正是告知卡红线 6 明令禁止的**（「候选人端出现任何分档结论或逐维度打分」）。
**在不放宽红线 6 的前提下，B 的数据来源不成立。**

#### B.2 即便硬做，字段完整性会丢什么

- JSON 截图会丢缩进与换行；手机字体缩放、滚动截图截半屏、手抖截歪 → 文本行缺失、字符截断。
- 人工/OCR 誊写错误率随字段量上升（本 JSON 有 m1/m2/m3 三块嵌套结构 + `idLast4`/`code`/`date` 等标识字段）。
- 施测人入口要的是 `JSON.parse` 成功且 `REP.build` 能跑（`app.js:426-436`）→ **截图转录的文本只要有一处语法错，整份报告就出不来**。

#### B.3 二次编辑与"P 图改分"

| 问题 | A | B |
|---|---|---|
| 改内容 | 改 JSON 里的分数 → 结构乱、`m1.dims` 与 `grade` 对不上、报告页能看出异常；且 `code`/`date` 改不了就会对不上登记表 | **改数字毫无痕迹**：截图里的 `score: 18` 改成 `20`，没有任何东西能发现 |
| 原始件是否留存 | 有（受控目录里的原文件） | ✗ 无 |
| 是否有校验指纹 | **无**（当前结果 JSON **没有 hash 字段**，schema 见 `app.js:400-409`） | 无 |
| 谁改的 | 无法证明，但**可以对账**：原文件 + `code` + 登记表 | 无法对账 |

⇒ **当前成品没有任何防篡改机制**（无 hash、无签名、时间戳只有 `date`）。
A/C 的"防篡改"实际靠的是**"手里有一份可与 `code` 对账的原件 + 字段结构自洽"**，不是密码学。
**若要真防篡改，必须给结果 JSON 加一个校验字段（改 `resultObj()`），那是另一张票的事 —— 本材料不提议。**

**若维护者坚持保留 B，可接受的降级定位（B′）**：
**截图只作辅证、不作数据源。** 施测人凭截图人工登记，`result_json` 列写「无（截图）」，
该样本 `exclude_reason` 写「仅截图回收，不进统计」。⇒ B 从"回传方案"降级为"登记备注"。

#### B.4 隐私暴露面（B 最差）

- 截图会进**相机胶卷**，而手机相册默认开云同步（iCloud 照片 / 相册云备份）⇒ 结果 JSON 里的 **`name`（姓名）、`idLast4`（身份证后 4 位）、`code`** 会被候选人自己上传到第三方云备份。
- 告知卡 §1 的载体清单与 §4 的留存表**完全没有这一类载体**（相册 / 云备份 / 截屏图库）。
- PIPL 第 17 条（告知）：相册云备份是**新的第三方处理者**，告知卡第 5 条现在的「不上传服务器」在 B 下会**名不副实** —— 不是施测人上传的，但结果是候选人自己传出去的。

#### B.5 完成页文案草稿（若保留 B）【提案 · 待拍板】

> ```
> ① 怎么交：点「下载结果文件（JSON）」，打开这个文件，把里面的文字截图。
> ② 交给谁：发给你收到测评的那位同事（微信 / 企微 / 邮件都可以）。
> ③ 多久收：交卷后请在 {当场 / 最迟当天 __ 前} 交给施测人。
> ```
> ⚠ 现状完成页**没有**"打开 JSON 查看文本"这一步的引导（候选人看不到结果、也不需要打开文件）。要落 B，完成页得**新增一条引导** ⇒ 那就是候选人端的额外操作与额外暴露面。
> ⚠ 而且 B 与红线 6 的冲突**不因改文案而消失** —— 冲突在"候选人看得见结果"这件事本身。

#### B.6 施测人现场话术草稿【提案 · 待拍板】

> 「麻烦您把结果**文件**发给我——我要的是文件本身，**截图不行**，因为截图我这边没法算分。
> （若维护者决定走 B′）那这样，您截图发我，我这边**只做个登记**，这份数据不进我们的统计口径。」

#### B.7 回收时限、责任人、成本

- 时限：与 A 同（当场 10 分钟内），因为人在现场。
- 责任人：主责当场施测人；备份试测负责人。但**数据质量责任人无处可落**（没有原件可对账）。
- 被试技术要求：**看似最低、实际最高** —— 要会打开文件管理器/文本编辑器找到 JSON 并截图（还要能截全）。
- **结论：B 不适合作为主路径。**

### 方案 C：施测人直取（同一台机器 / 局域网 / 移动介质）

#### C.0 一句话定性

**"直取"在浏览器里其实是三条完全不同的路，只有 C1（移动介质当场取文件）真正好用；C3（局域网）会撞告知卡红线 7，是三个方案里隐私口径最脆的一个。**

#### C.1 三条子路径的差别

| 子路径 | 做法 | 前置条件 | 可行性 |
|---|---|---|---|
| **C1 移动介质**（U 盘 / 数据线 / 共享文件夹） | 候选人点下载 → 文件落到设备的"下载"目录 → 拷到施测人带来的介质或现场共享文件夹 | 施测人自备 ≥1 个 U 盘（或数据线）；现场有施测人电脑做改名与归档；候选人设备允许访问下载目录 | **高**。离线、无账号、无第三方、当场可完成 |
| **C2 局域网直取** | 施测人机器开共享/本地服务，候选人设备把下载目录共享出来 | IT 许可；网络连通；共享账号密码；**下载目录在共享路径内** | **低**。企业网通常禁开共享；且结果**过了网络** |
| **C3 同一台机器上直接读** | 施测人在**候选人那台设备**上打开施测人入口 → `openReport()` 会用**该设备本地的 `S`** 直接生成报告 | 候选人把设备交给施测人操作 | ⚠ **能跑通，但撞红线 6**：报告（分数/档位/短板）会**显示在候选人设备上**，且报告页有打印/存 PDF ⇒ 候选人可截图带走、可打印带走 |

**C3 的一个技术细节值得记下**：`openReport()` 在粘贴框为空时用当前设备的 `S` 出报告（`app.js:431-433`）。
这条路径确实能在候选人设备上"直取"结果，但**代价是把报告暴露给候选人** —— 按告知卡 §1，报告页属于"离开候选人设备"的载体，红线 6 又禁止候选人端出现分档结论。
⇒ **C3 只可作为"在候选人设备上点一次下载"，不可作为"在候选人设备上看报告"。**

#### C.2 前置条件清单（C1）

1. 施测人自备 **≥1 个 U 盘**（或一根数据线），**编号登记**：谁拿的、编号、什么时候归还清零。
2. 现场有 **一台施测人电脑**：负责改名（§六 6.2）、落受控目录、跑 `ingest_real.py` 转换。
3. 候选人设备能"下载文件"且下载目录可访问：
   - iOS Safari → 下载到「文件」App（路径深，**候选人自己常常找不到 —— 这正是 C1 的真正价值**）；
   - Android → `Download` 目录；
   - 桌面浏览器 → `~/Downloads`。
4. 候选人同意"让施测人拷走这个文件" —— **这一步要进告知卡与现场话术**（结果离开设备的方式变了）。
5. 介质归还后**当场清零**（格式化 / `diskutil eraseDisk`），并在登记表或介质登记表上记归还时间。
6. C2 若被选中，另需：IT 书面许可、一台固定"中转机"、明确禁止公网。

#### C.3 完成页文案草稿（C1）【提案 · 待拍板】

> ```
> ① 怎么交：点「下载结果文件（JSON）」，把文件放在这台设备上就行，不用发。
> ② 交给谁：我（施测人）会在这台设备上把它拷走，你不用做任何操作。
> ③ 多久收：交卷后请在 {当场} 留在座位上，等我把文件拷走并登记完成；{最迟 __ 前} 拷走。
> ```

#### C.4 施测人现场话术草稿（C1）【提案 · 待拍板】

> 「最后一小步：这个文件现在在您的设备上。**不用您发给我**，我拿 U 盘拷一下就行。
> 请您点一下『下载结果文件』，然后把手机给我三十秒——我拷到 U 盘上，拷完当场还给您。
> 拷完您点一下『清除本机数据』，手机上的记录就删掉了。
> 您报一下屏幕上那个测评编号 `EQ-……`，我按编号对账。
> 三十秒就好，不会动您的其他东西。」

#### C.5 回收时限与责任人【提案 · 待拍板】

- 时限：**当场 10 分钟内**（比 A 略紧，因为是物理在场）。
- 主责：当场施测人（拷文件 + 改名 + 登记）；**介质管理另设一人**（登记、归还、清零）—— 建议由试测负责人兼。
- 逾期未交：与 A 同（记 `exclude_reason`，该份作废）。

#### C.6 隐私 / PIPL 影响

- **新增载体类型**（U 盘 / 中转机 / 现场共享目录）⇒ 告知卡 **§1 载体清单必须新增行**，**§4 留存表必须新增行**（谁拿、何时清零、留存期）。
- 告知卡第 5 条「只在本机、不上传服务器、需主动回传」：
  - **C1**：基本成立（U 盘是物理搬运，不是上传）—— 但"结果会经由施测人携带的移动介质离开你的设备"这句**必须补写**。
  - **C2**：**这句变得不成立** —— 结果**过了网络**（虽不出单位网）。⇒ 必须改成「不经过任何第三方或互联网服务；如采用局域网直取，则只在本单位内部网络内传输」。**这是三个方案里唯一会让告知卡第 5 条产生"表述不实"风险的方案**，按 PIPL 第 17 条（限时口径笔记所载要点）属"告知不真实"项下的问题。
- 告知卡第 2 条（谁能看到结果）：C 不新增人，**不变**。
- ADR-0004：C 不引入身份标识 → **不冲突**（文件名带姓名的问题同 A，见 §六 6.2）。
- PIPL 第 24 条：与 A 相同判断，**不因回传方式改变**。

#### C.7 失败模式与兜底

| 失败模式 | 现象 | 兜底 |
|---|---|---|
| 设备没空间 / 下载失败 | 手机存储满 | 换设备？**不得**（会换掉作答环境）→ 改走 A 的邮件 |
| 找不到下载目录 | iOS「文件」App 层级深 | 这正是 C1 存在的理由：**施测人自己找**，不必麻烦被试 |
| U 盘插上读不到 | iPhone 需「文件」App 才能看到 U 盘；Android 需 OTG | 备一根数据线；或退到 A |
| 拷到一半断连 | 线松 / 手机息屏 | 重拷；**拷完必须校验 9 个字段齐全**（作业包 §三） |
| 拷串号 | 上一份的文件还在 U 盘 | 拷完立刻改名成 `EQ-{code}.json`（§六 6.2）→ 串号当场暴露；每拷一份清一次介质 |
| U 盘丢失 / 带病 | — | 介质编号登记 + 归还清零 + 只收 JSON 不收其他文件 + 拷完扫描 |
| C2 共享开不了 | IT 禁开共享 | C2 直接不选，退 C1 |

#### C.8 成本（对被试的技术要求）

- **被试负担最低**：点一次下载 + 允许施测人拷文件（+ 可选：点清除本机数据）。
- **施测人负担最高**：要带介质、要有一台电脑、要管介质编号与清零、要在 iOS/Android 的差异里找文件。
- ⇒ **总成本未必比 A 低**，只是成本从被试挪到了施测人。

## 四、我的推荐【建议 · 最终由维护者拍板】

### 4.1 推荐内容

**主案 A（回传结果 JSON 文件，微信/企微/邮件），兜底 C1（施测人自带 U 盘当场取文件），B 不进数据流程（最多降级为 B′ 辅证登记）。**

理由（按权重）：
1. **数据可用性**：施测人入口要的是完整 JSON（`app.js:426-436`）。A 与 C 拿得到，B 拿不到 —— **这是唯一的硬性淘汰项**。
2. **红线合规**：B 直接撞红线 6；C2 撞红线 7。只有 A 与 C1 干净。
3. **当场回收**：票 #26 是"现场发放 + 当场回收"，A 与 C 都能在 10 分钟内闭环。
4. **被试负担**：样本是 HR/管理岗 + 在职员工（专员/经理/总监），微信是基本盘 ⇒ **A 的被试负担最低**（C1 更低，但施测人负担高、总成本不一定低）。
5. **改动量最小**：A 只需改 `copy.js` 一条文案 + 告知卡补几行；B 要动红线与 schema。

### 4.2 推荐成立的前提条件【逐条可验证】

| # | 前提 | 不成立时怎么办 |
|---|---|---|
| **P1** | 被试以内部候选人（HR/管理岗）与在职员工为主，手机上有微信/企微，**且愿意用聊天工具传一个文件** | 切 **C1**（人还在现场，直接拷文件），**不要**切 B |
| **P2** | 组织允许结果文件经**施测人个人微信/企微/邮箱**中转，且施测人承诺**回收即从聊天记录删除、转入受控目录** | 改走**邮件**（自带送达留痕，边界在 HR 侧邮箱）；再不行只剩 C1 |
| **P3** | 现场有一台施测人电脑（改名、落受控目录、跑 `ingest_real.py`） | 先解决这一项，否则 A/C 都没有归档落点 |
| **P4** | **结果文件名统一为 `EQ-{测评编号}.json`**（见 §六 6.2），避免姓名经 `result_json` 列间接进 CSV | 若不采纳，则需在告知卡 §4 留存表与 `ingest_real_说明.md` §六 限制 1 上另开口子（**那要另开改动**） |
| **P5** | 现场提醒候选人点「清除本机数据」这一步能说清 | 不成立也不影响数据回收，但本机残留时间会变长 |

### 4.3 如果前提不成立

**备选顺序：A → C1 → B′（仅辅证）。** 任何情况下都**不建议**把 B 当数据源。

### 4.4 维护者拍板时需要一并定的（否则 SOP 落不了地）

1. **回收时限的具体值**（当场 10 分钟？最迟当天 18:00？催收 1 次？）
2. **逾期未交是否即作废**（本稿建议作废并记 `exclude_reason`）。
3. **文件名是否统一为 `EQ-{测评编号}.json`**（涉及 `copy.js` 一句话 + `app.js` 下载名 —— 属另开改动）。
4. **B 是否降级为 B′**（只登记不进统计）。
5. **告知卡"结果回传方式"是否从"可选要素"升为"必含要素"**（本稿建议升，见 §五 5.1）。
6. **`answers` 列的数据来源**（§六 6.3 —— **仓内未找到依据，本票解决不了**）。

### 6.2 「结果 JSON 文件名」这一环（专门展开）

**现状**
- 成品下载文件名 = `核心人才系列测试_<候选人自填姓名>.json`（`app.js:413`）。
- 登记表 `result_json` 列的既有定义 = 「结果 JSON 文件名（归档用）」（`ingest_real_说明.md` §三）；`ingest_real.py` 对该列**只做缺失提醒，不校验内容**。
- ⚠ **冲突**：`ingest_real_说明.md` §六 限制 1 明确「**姓名不在本 CSV 表头里**」「要归档带姓名的登记表，就在这份 CSV 之外另存一份带姓名的表」。若 `result_json` 列填**含姓名的默认文件名**，**姓名会通过这一列间接进 CSV**，与该限制相悖。

**提案【待拍板】**：**统一文件名为 `EQ-{测评编号}.json`**
- 编号在完成页已显示（`app.js:282`），也在文件内 `code` 字段 —— **双源可核**，正好当对账锚点。
- A 路径：候选人在完成页改名后再发（需在 `sendBody` 写一句，见 §A.2 ①）。
- C1 路径：施测人拷完立即改名，候选人不必会改名。**C1 在这一点上负担更低。**
- 登记表 `result_json` 列**填规范名**（不含姓名）；原名（如有）记进 `quality_note`。
- **这属于改 `app.js` 下载名 + `copy.js` 文案 + 登记表口径的三处联动，按本票约定属"拍板后另开改动"，本稿只登记不动手。**

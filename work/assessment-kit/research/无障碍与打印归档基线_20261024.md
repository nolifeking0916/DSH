# 无障碍与打印归档基线（自包含单文件招聘测评 HTML）

> **一句话结论**：本工具的无障碍硬底线是「文本对比度 ≥ 4.5:1（大字号 ≥ 3:1）、图形与控件边界 ≥ 3:1、指针目标 ≥ 24×24 CSS px、聚焦组件不得被作者内容「完全」遮挡且焦点指示器始终可见、必答缺失必须用**文本**描述错误」；打印侧只有 `@page` 的 `margin` / `size` 与 `break-inside: avoid` / `break-before: page` 具备跨浏览器可用性，`@page` 的 margin box（页眉页脚 + `counter(page)`）在 Firefox 与 Safari 至今**完全不支持**，`print-color-adjust: exact` 只是给 UA 的**提示**而非保证；移动端必须用 `env(safe-area-inset-*)` 避让刘海与 Home 指示条、用 `100dvh` / `100svh` 而非 `100vh` 应对地址栏收缩。

## 0. 证据等级、来源口径与调研方法

- **只采一手来源**：规范正文（W3C TR / CSSWG Editor's Draft）、W3C WAI 官方 Understanding 文档、厂商官方文档（Apple / Google）、以及 Mozilla 官方数据集 MDN browser-compat-data。二手综述、博客转述、个人教程一律未采用。
- **规范状态必须随结论一起引用**，因为「规范写了」≠「浏览器做了」：
  - WCAG 2.2 — **W3C Recommendation, 12 December 2024**
  - CSS Paged Media Module Level 3 — **W3C Working Draft, 14 September 2023**（注意：仍是 WD，非 REC）
  - CSS Fragmentation Module Level 3 — **W3C Candidate Recommendation, 4 December 2018**
  - CSS Color Adjustment Module Level 1 — **W3C Candidate Recommendation Snapshot, 16 December 2025**
  - CSS Values and Units Module Level 4 — **W3C Working Draft, 12 March 2024**
  - SVG 2 — **W3C Candidate Recommendation Snapshot, 06 October 2026**
- **浏览器支持矩阵**统一取自 MDN browser-compat-data（`mdn/browser-compat-data` 仓库 JSON），这是 Mozilla 维护的官方支持数据，不是第三方测评站。
- **标注约定**：任何没有一手依据的判断，文中显式写「**未找到官方依据**」，不做推测性断言。

## 1. 无障碍（WCAG 2.2）

### 1.2 1.4.3 对比度（最小）——阈值与判定要点

规范原文（Level AA）：

> The visual presentation of text and images of text has a contrast ratio of at least 4.5:1, except for the following:
> **Large Text** — Large-scale text and images of large-scale text have a contrast ratio of at least 3:1;
> **Incidental** — Text or images of text that are part of an inactive user interface component, that are pure decoration, that are not visible to anyone, or that are part of a picture that contains significant other visual content, have no contrast requirement.
> **Logotypes** — Text that is part of a logo or brand name has no contrast requirement.

来源：[WCAG 2.2 §1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum)

判定要点（官方 Understanding 文档）：

- **大字号定义**（WCAG 2.2 术语表 `large scale (text)`）：至少 **18 point** 或 **14 point bold**，或对中日韩（CJK）字体有同等视觉效果。Understanding 补充换算：`1pt = 1.333px`，因此 14pt ≈ **18.5px**、18pt ≈ **24px**。来源：[WCAG 2.2 术语表](https://www.w3.org/TR/WCAG22/#dfn-large-scale) ｜ [Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- **不得四舍五入**：`the computed values should not be rounded (e.g., 4.499:1 would not meet the 4.5:1 threshold)`。判定必须用未舍入的计算对比度。来源：[Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- 对比度应按 **sRGB 色彩空间**评估；若使用其他色彩空间需另见 Understanding 1.4.3。来源：[WCAG 2.2 §1.4.3 注记](https://www.w3.org/TR/WCAG22/#contrast-minimum)

### 1.3 1.4.11 非文本对比度 —— 在雷达图 / 条形图上的适用

规范原文（Level AA）：

> The visual presentation of the following have a contrast ratio of at least 3:1 against adjacent color(s):
> **User Interface Components** — Visual information required to identify user interface components and states, except for inactive components or where the appearance of the component is determined by the user agent and not modified by the author;
> **Graphical Objects** — Parts of graphics required to understand the content, except when a particular presentation of graphics is essential to the information being conveyed.

来源：[WCAG 2.2 §1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast)

对图表的官方判定要点（Understanding 1.4.11）：

- **3:1 是阈值，不四舍五入**：`2.999:1 would not meet the 3:1 threshold`。来源：[Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- **「graphical object」的具体含义**：独立图标（如打印图标），以及复杂图形中理解内容所必需的重要部分——官方举例明确包含「**a graph 中的每一条线**」「图表中标记网格的灰线」「饼图中彼此需要区分的各扇区」。来源：[Understanding 1.4.11 — Graphical Objects](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- **不是所有图形都要达标**：只有「用户为了理解图形所传达的信息而必须察觉」的部分才需要 3:1；装饰性、重叠的次要图形可依 Gestalt 连续性原则忽略。来源：同上
- **焦点指示器受 1.4.11 约束**：若半透明遮罩/模糊遮罩与聚焦项重叠，即使未完全遮挡（仍过 2.4.11），也可能不满足 1.4.11。来源：同上
- **控件边界不一定要有**：若控件本身有足够对比的文字/图标可识别，则不必额外画边界；只有在「没有其他视觉方式识别控件存在」时才必须有边界，且该边界需满足 3:1。来源：同上
- **焦点指示器本身**：Understanding 举例 —— 灰色 `#949494` 对白色 = 3:1 的焦点指示器合格。来源：同上

### 1.4 2.4.7 焦点可见 / 2.4.11 焦点不被遮挡 —— 移动端 sticky 头部的典型情形

规范原文：

> **2.4.7 Focus Visible (AA)** — Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible.
> **2.4.11 Focus Not Obscured (Minimum) (AA)** — When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content.
> **2.4.12 Focus Not Obscured (Enhanced) (AAA)** — When a user interface component receives keyboard focus, no part of the component is hidden by author-created content.

来源：[WCAG 2.2 §2.4.7](https://www.w3.org/TR/WCAG22/#focus-visible) ｜ [§2.4.11](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum) ｜ [§2.4.12](https://www.w3.org/TR/WCAG22/#focus-not-obscured-enhanced)

关于 sticky 头部遮挡的官方说明（Understanding 2.4.11）：

- **典型遮挡源**：`Typical types of content that can overlap focused items are sticky footers, sticky headers, and non-modal dialogs.` 来源：[Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)
- **作者预置内容（如 sticky 头部）不能免责**：规范 Note 2 只豁免「用户自己打开的内容」；Understanding 明确：`Content pre-positioned by the author (such as a sticky footer) ... must not prevent the item receiving focus from being immediately visible in the viewport.` 来源：同上
- **官方认可的规避手法**：
  - `scroll padding` —— `using scroll padding so the banner does not overlap other content`；官方通过示例即为「sticky footer + 使用 scroll padding 让滚动内容始终露出焦点项」。来源：同上
  - 官方技术条目：**C43: Using CSS scroll-padding to un-obscure content**；失败条目 **F110: Failure of Success Criterion 2.4.11 Focus Not Obscured (Minimum) due to a sticky footer or header completely hiding focused elements**。来源：同上
- **可移动内容只按初始位置判定**（Note 1）：`only the initial positions of user-movable content are considered for testing and conformance`。来源：[WCAG 2.2 §2.4.11 Note 1](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum)
- **本准则只看组件本体，不看焦点指示器**：`The component itself does not include the focus indicator when checking that "the component is not entirely hidden" ... However, if the focus indicator is fully obscured, it would likely fail 2.4.7 Focus Visible.` 来源：Understanding 2.4.11

### 1.5 2.5.8 目标尺寸（最小）—— 具体像素值与判定算法

规范原文（Level AA）：

> The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when:
> **Spacing** — Undersized targets (those less than 24 by 24 CSS pixels) are positioned so that if a 24 CSS pixel diameter circle is centered on the bounding box of each, the circles do not intersect another target or the circle for another undersized target;
> **Equivalent** — The function can be achieved through a different control on the same page that meets this criterion;
> **Inline** — The target is in a sentence or its size is otherwise constrained by the line-height of non-target text;
> **User Agent Control** — The size of the target is determined by the user agent and is not modified by the author;
> **Essential** — A particular presentation of the target is essential or is legally required for the information being conveyed.

来源：[WCAG 2.2 §2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum)

官方判定算法（Understanding 2.5.8）：

- **达标的几何定义**：`it must be conceptually possible to draw a solid 24 by 24 CSS pixel square, aligned to the horizontal and vertical axis such that the square is completely within the target`。圆角导致画不出 24×24 方块 → 视为 undersized，只能靠 Spacing 例外通过。来源：[Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- **undersized 的间距判定**：以目标 bounding box 中心为圆心、直径 **24 CSS px** 的圆，圆不得与另一目标或另一 undersized 目标的圆相交。来源：同上
- **与页面缩放无关**：`The requirement is independent of the zoom factor of the page; when users zoom in, the CSS pixel size of elements does not change.` 不能靠用户放大来「凑够」。来源：同上
- **官方建议**：`As a best practice it is recommended to at least meet the minimum size requirement of the Success Criterion, regardless of spacing. For important links/controls, consider aiming for the stricter 2.5.5 Target Size (Enhanced).` 来源：同上
- **间距可替代尺寸**：官方解释 `20×20` 且相邻留 **4px** 间距可过 Spacing 例外；`20×20` 无间距则失败。来源：同上

### 1.6 3.3.7 冗余输入 —— 同一信息已填过则不应要求重填

规范原文（Level A）：

> Information previously entered by or provided to the user that is required to be entered again in the same process is either:
> - auto-populated, or
> - available for the user to select.
> Except when:
> - re-entering the information is essential,
> - the information is required to ensure the security of the content, or
> - previously entered information is no longer valid.

来源：[WCAG 2.2 §3.3.7](https://www.w3.org/TR/WCAG22/#redundant-entry)

官方边界说明（Understanding 3.3.7）：

- **浏览器自动填充不算数**：`The autocomplete feature of browsers is not considered sufficient because it is the content (the website) that needs to provide the stored information`。来源：[Understanding 3.3.7](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)
- **「同一流程」的界定**：`This success criterion does not add a requirement to store information between sessions. A process is defined on the basis of an activity and is not applicable when a user returns after closing a session or navigating away.` 来源：同上
- **「可供选择」的合法形态**：从下拉选择、从页面上选取并复制文本、勾选「同上一项」复选框来填充同值字段。来源：同上
- **PII 提醒**：本准则不设 PII 专项例外，但实现自动填充时作者应保证过程内临时存储的数据保护。来源：同上

### 1.7 4.1.3 状态消息 —— 答完 / 必答提示 / 模块切换是否需要 live region

规范原文（Level AA）：

> In content implemented using markup languages, status messages can be programmatically determined through role or properties such that they can be presented to the user by assistive technologies without receiving focus.

来源：[WCAG 2.2 §4.1.3](https://www.w3.org/TR/WCAG22/#status-messages)

「状态消息」的官方定义（WCAG 2.2 术语表）：

> change in content that is not a change of context, and that provides information to the user on the success or results of an action, on the waiting state of an application, on the progress of a process, or on the existence of errors

来源：[WCAG 2.2 术语表 `status message`](https://www.w3.org/TR/WCAG22/#dfn-status-message)

对「逐题翻页」场景的官方判定（Understanding 4.1.3）：

- **会改变上下文的切换不属状态消息**：`messages that involve changes of context do not need to be considered and are not within the scope of this success criterion`，因为上下文变化本身会移动焦点、辅助技术已自动播报。来源：[Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **用户交互导致的内容显隐不属状态消息**：`Content is exposed or hidden when a user interacts with a user interface component, for example expanding components such as a menu, select, accordion or tree, or selecting a different tab item in a tablist.` → **模块切换（tab）本身不需要 live region**。来源：同上
- **官方技术条目映射**：
  - 动作成功/结果、应用状态 → **ARIA22: Using role=status**
  - 建议、警告、错误存在 → **ARIA19: Using ARIA role=alert or Live Regions to Identify Errors**
  - 过程进度 → **ARIA23: Using role=log** / **ARIA25: Using an ARIA live region to convey the status of a progress bar**
  - 来源：同上
- **官方警告**：`A role of "alert" is only necessary where a change of context does not take place.` 以及 `there is a risk of making an application too "chatty" for a screen reader user`。来源：同上
- **非文本状态**：图标/声音表达的状态需按 1.1.1 提供文本替代 + 适当的 role。来源：同上

### 1.8 与「单题翻页式表单」直接相关的准则 —— 对「下一题按钮在未作答时置灰」的含义

**结论：把「下一题」按钮置灰（`disabled`）本身并不违反 WCAG，但会让用户拿到一个「无解释的坏掉控件」，与 3.3.1 / 4.1.3 的组合要求冲突。**

支撑依据：

1. **必答未填 = input error，必须用文本描述**。Understanding 3.3.1 明确把「required by the web page but omitted by the user」列为 input error，并要求 `the error must be indicated in text`；同一条 Understanding 指出「仅重新显示表单而不给出提交失败的提示」不足以通过。来源：[Understanding 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)
2. **3.3.3 Error Suggestion（AA）**：`If an input error is automatically detected and suggestions for correction are known, then the suggestions are provided to the user`。Understanding 给出可直接照用的文案对照：`"Email is not valid"` 通过 3.3.1；`"Please provide a valid email address in the format name@domain.com"` 同时通过 3.3.1 与 3.3.3。来源：[WCAG 2.2 §3.3.3](https://www.w3.org/TR/WCAG22/#error-suggestion) ｜ [Understanding 3.3.3](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html)
3. **置灰控件对辅助技术不播报**：disabled 控件不会获得焦点，其状态变化也不是「状态消息」，用户无法从 `aria-live` 得到「本题未作答」的提示。因此**错误文本必须独立于按钮状态存在**（可见文本 + 与出错项的程序化关联）。来源：[Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)（`not a status message` 的界定）｜ [WCAG 2.2 §4.1.2](https://www.w3.org/TR/WCAG22/#name-role-value)
4. **焦点顺序（2.4.3, A）**：切题时若把焦点移到新题，焦点顺序必须与阅读顺序一致；若把焦点留在按钮上，用户无法察觉题面已变。来源：[WCAG 2.2 §2.4.3](https://www.w3.org/TR/WCAG22/#focus-order)
5. **输入时自动改变上下文（3.2.2, A）**：`Changing the setting of any user interface component does not automatically cause a change of context unless the user has been advised of the behavior before using the component.` —— 单选后**自动跳下一题**属于「改变设置引发上下文变化」，除非事先告知用户。来源：[WCAG 2.2 §3.2.2](https://www.w3.org/TR/WCAG22/#on-input)
6. **获得焦点不得自动改变上下文（3.2.1, A）**：`When any user interface component receives focus, it does not initiate a change of context.` —— 焦点样式不得触发翻页/跳模块。来源：[WCAG 2.2 §3.2.1](https://www.w3.org/TR/WCAG22/#on-focus)
7. **错误定位**：3.3.1 要求 `the item that is in error is identified` —— 「第 7 题未作答」这种定位信息必须同时出现在错误文本中，并与题号面板中的第 7 项关联。来源：[Understanding 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)

### 1.9 2.4.11 与 2.5.8 的精确措辞差异（并排对照）

| 维度 | **2.4.11 Focus Not Obscured (Minimum)** | **2.5.8 Target Size (Minimum)** |
|---|---|---|
| 原文 | `When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content.` | `The size of the target for pointer inputs is at least 24 by 24 CSS pixels, except when: …` |
| 触发条件 | **键盘焦点**落到组件上 | **指针输入**（触摸/鼠标）落在目标上 |
| 约束对象 | 空间位置（是否被作者内容遮挡） | 几何尺寸（目标有多大） |
| 阈值性质 | 定性：无阈值像素值，用 `not entirely hidden` / `no part … is hidden` 区分 AA/AAA | 定量：**24 × 24 CSS px**（AAA 版 2.5.5 为 **44 × 44 CSS px**） |
| 例外机制 | 规范 Note 2：用户自己打开的内容可遮挡；Note 1：可移动内容只按初始位置判定 | 规范列出 **5 项例外**：Spacing / Equivalent / Inline / User Agent Control / Essential |
| 判定对象 | 组件**本体**（不含焦点指示器） | 目标的 bounding box（须能画出轴对齐的 24×24 实心方块） |
| 补救手段（官方） | `scroll padding`（C43）；sticky 头部完全遮住聚焦项 = 失败条目 F110 | undersized 目标用 **24 CSS px 直径圆**做间距判定；换更大目标或加间距 |
| 等级 | AA | AA |
| 一手来源 | [§2.4.11](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum) ｜ [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | [§2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum) ｜ [Understanding](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) |

**要点**：两者可以同时失败——一个 20×20 px 的「下一题」按钮既违反 2.5.8（尺寸），在被 sticky 头部完全盖住时又违反 2.4.11（遮挡）；修好其中一个并不能通过另一个。

### 2.2 `@page` 规则能设置什么

规范原文（§4.1）：

> Authors can specify various aspects of a page box, such as its dimensions, orientation, and margins, within an `@page` rule. `@page` rules are allowed wherever rule-sets are allowed.
> An `@page` rule consists of the keyword `@page`, an optional comma-separated list of page selectors and a block of declarations (said to be in the **page context**).
> … The current level of this specification only allows **margin at-rules** inside `@page`.
> `@page` rules without a selector list apply to every page.
> … The `@page` rule can only contain **page properties and margin at-rules**.

来源：[CSS Paged Media Module Level 3 §4.1](https://www.w3.org/TR/css-page-3/#at-page-rule)

要点：

- **可设置项**：`margin`（含 `margin-top/right/bottom/left`）、`size`（含 `portrait`/`landscape`/命名纸张如 `A4`/`letter`）、`page-orientation`、`page`（命名页引用）。
- **页面选择器**：`@page :left` / `:right` / `:first` / `:blank`，以及 `@page <page-type>` 命名页；`:blank` 只能由 `break-before/after` 的 `left/right/recto/verso` 产生。来源：[§4.2](https://www.w3.org/TR/css-page-3/#page-selectors)
- **层叠与优先级**：page context 的声明像普通元素声明一样层叠；选择器特异性按 (f, g, h) 三元组比较（f = 命名页类型数，g = `:first`/`:blank` 数，h = `:left`/`:right` 数）。官方例子：`@page :blank { @top-center { content: none } }` 由于 `:blank` 特异性高于 `:right`，即使写在前面也会胜出。来源：[§4.4](https://www.w3.org/TR/css-page-3/#at-page-rule)
- **命名页用法**：`@page narrow { size: 9cm 18cm }`，元素用 `page: narrow` 指定落入该页；`page` 属性**不继承**。来源：[§8.1](https://www.w3.org/TR/css-page-3/#named-page)

### 2.3 margin box（页眉页脚）与 `counter(page)` / `counter(pages)`

- **共 16 个 page-margin box**：top-left-corner / top-left / top-center / top-right / top-right-corner / bottom-left-corner / bottom-left / bottom-center / bottom-right / bottom-right-corner / left-top / left-middle / left-bottom / right-top / right-middle / right-bottom。来源：[§5](https://www.w3.org/TR/css-page-3/#page-margin-boxes)
- **margin box 可以像伪元素一样生成内容**，用于页眉页脚、页码。
- **`counter(page)`**：规范原文 `A counter named page is automatically created and incremented by 1 on every page of the document, unless the counter-increment property in the page context explicitly specifies a different increment for the page counter.` 并说明它是真实计数器，可在 `counter()` / `counters()` 中使用。来源：[§6.1](https://www.w3.org/TR/css-page-3/#page-based-counters)
- **`counter(pages)`**：规范原文 `Additionally, a counter named pages is automatically created by the UA. Its value is always the total number of pages in the document. (In continuous media this is always 1.) The value of pages cannot be manipulated.` 来源：同上
- **默认对齐**（UA 默认样式表）：`@top-center` 为 `text-align: center`，`@bottom-center` 为 `text-align: center`，`@top-left` 为 `left`，`@top-right` 为 `right` 等。来源：[§6.2](https://www.w3.org/TR/css-page-3/#page-margin-boxes)

### 2.5 `print-color-adjust` / `color-adjust` —— 规范状态与浏览器支持

规范原文（CSS Color Adjustment Module Level 1 §4.1）：

> The `print-color-adjust` property provides a **hint** to the user-agent about how it should treat color and style choices that might be expensive or generally unwise on a printer or similar device, such as using light text on a dark background.
> If user agents allow users to control this aspect of the document's display, **the user preference must be respected more strongly than the hint provided by `print-color-adjust`**.
> **economy** — The user agent should make adjustments to the page's styling as it deems necessary and prudent for the output device. For example, if the document is being printed, a user agent might ignore any backgrounds and adjust text color to be sufficiently dark, to minimize ink usage.
> **exact** — This value indicates that the page is using color and styling on the specified element in a way which is important and significant, and which should not be tweaked or changed except at the user's request.
> UAs must propagate the `print-color-adjust` value set on the **root element** to the document viewport (where it can affect e.g. the canvas background). **Note that `print-color-adjust` is not propagated from HTML body.**

来源：[CSS Color Adjustment L1 §4.1](https://www.w3.org/TR/css-color-adjust-1/#print-color-adjust)

- `color-adjust` 简写：规范原文 `The color-adjust shorthand is currently deprecated. Authors should use the more specific print-color-adjust property`。来源：[§4.2](https://www.w3.org/TR/css-color-adjust-1/#color-adjust)

**规范层面「打印掉色」的根本原因**：初始值就是 `economy`，UA 被规范明确允许「ignore any backgrounds and adjust text color」。`exact` 只是把「希望保留颜色」的意图告诉 UA，**不是保证**。

**浏览器层面的两条硬事实**（MDN browser-compat-data 的 notes 字段，来自各 UA 的实际行为）：

- Chrome（`-webkit-print-color-adjust` 自 17 起）：`Chrome does not print backgrounds of the <body> element. If this property is set to exact for the <body> element, it will apply only to its descendants.`
- Safari（`-webkit-print-color-adjust` 自 6 起）：`Safari does not print backgrounds of the <body> element. If this property is set to exact for the <body> element, it will apply only to its descendants.`
- 来源：[properties/print-color-adjust.json](https://github.com/mdn/browser-compat-data/blob/main/css/properties/print-color-adjust.json)

### 2.6 打印时 SVG 雷达图「丢色 / 变形」的规范层面成因与规避

**成因一：颜色（丢色）**
- 规范层面：`print-color-adjust` 初始值 `economy`，UA 可忽略背景并调整文字色；`exact` 只是 hint，用户/UA 偏好优先（见 §2.5）。
- 规避事实：不能依赖 `print-color-adjust` 单独保住图表配色；`<body>` 上的背景在 Chrome/Safari 本就不打印。
- 可靠的替代事实：颜色若承载**信息**（而不是装饰），必须同时用**非颜色编码**（数值标签、表格、纹理/图案、线型）冗余表达——这是 WCAG 1.4.1 Use of Color 的方向，但本节只标注「颜色承载信息时须有非颜色等价物」这一事实本身。

**成因二：尺寸（变形）**
- 规范层面（CSS Values 4 §6.1.2）：`The viewport-percentage lengths are relative to the size of the initial containing block—which is itself based on the size of either the viewport (for continuous media) or the **page area** (for paged media).` → 用 `vw/vh/%` 定的图表尺寸在纸面上按「页面区域」重算，与屏幕不同。来源：[CSS Values 4 §6.1.2](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)
- MDN `@page` 页给出同方向提示：`The W3C is discussing how to handle viewport-related length units, vh, vw, vmin, and vmax. Meanwhile do not use them within an @page at-rule.` 来源：[MDN `@page`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@page)
- 规范层面（SVG 2 §8.12）：`If either width or height are not specified, the used value is the initial value 'auto'. 'auto' and percentage lengths must not be used to determine an intrinsic width or intrinsic height.`；内在宽高比算法：绝对值 `width/height` → `viewBox` 宽高比 → `null`；且 `In all host contexts, the intrinsic aspect ratio, where available, must be respected when sizing the SVG viewport.` 来源：[SVG 2 §8.12](https://www.w3.org/TR/SVG2/coords.html#SizingSVGInCSS)
  - 推论：只给 `viewBox` 而不给确定 `width/height` 的 SVG 没有内在宽高，按 CSS Images 3 Default Sizing Algorithm 落到默认对象尺寸，容易在窄页面区域被缩放变形。
- 规避事实：图表在打印时必须使用**绝对/物理单位**（如 `mm`/`cm`）或明确的 `width`/`height` + `viewBox`，并使用 `break-inside: avoid` 保证不跨页切断。

**成因三：跨页切断**
- `break-inside: avoid`（`auto | avoid | avoid-page | avoid-column | avoid-region`）适用于除 inline-level boxes、internal ruby boxes、table column/column group boxes、绝对定位盒子外的所有元素；`avoid-page` 专用于分页语境。来源：[CSS Fragmentation L3 §3.2](https://www.w3.org/TR/css-break-3/#break-inside-property)

| 安全区与普通间距的合并 | Apple 官方推荐用 `max()` 取「普通间距」与「安全区内边距」的较大者 | 官方示例用 `@supports(padding: max(0px))` 做特性检测 | [WebKit 官方博客](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) |
| `viewport-fit` 的 W3C 规范地位 | **未找到 W3C 官方依据** | CSS Viewport Module Level 1（Editor's Draft）§3.1 列出的 viewport meta 属性只有 `width / height / initial-scale / minimum-scale / maximum-scale / user-scalable / interactive-widget`，**不含 `viewport-fit`** | [CSS Viewport Module L1 §3.1](https://drafts.csswg.org/css-viewport-1/#viewport-meta-element) |
| `100vh` 在移动端的问题 | `vh`/`vw` 尺寸不随 UA 动态工具栏变化，元素会「溢出视口」；工具栏收起时 `100vh` 才「正确」 | web.dev 原文：`elements sized to be 100vh tall will bleed out of the viewport` | [web.dev: The large, small, and dynamic viewport units](https://web.dev/blog/viewport-units) |
| `svh` / `lvh` / `dvh` | 三个视口尺寸概念：**large**（假定可收起 UI 全部收起）、**small**（假定全部展开）、**dynamic**（随 UI 展开/收起实时变化） | `sv*` 更安全；`dv*` 被夹在 `sv*` 与 `lv*` 之间；`v*`（无前缀）等同 **large** | [CSS Values 4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths) |
| `dv*` 的更新行为 | UA **不必**以 60fps 动画 `dv*`；推荐在 UI 动画期间按完全收起尺寸计算 | 官方建议 `it is recommended that UAs assume the fully-retracted size for this duration` | [CSS Values 4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths) |
| 动态视口单位的落地时间 | 这些单位随 **Chrome 108** 发布，Safari 与 Firefox 更早已支持 | web.dev 原文：`These units ship in Chrome 108, joining Safari and Firefox which already have support.` | [web.dev](https://web.dev/blog/viewport-units) |
| 触控目标尺寸 | WCAG 2.5.8 已覆盖：≥ **24×24 CSS px**（AA）；2.5.5 为 **44×44 CSS px**（AAA） | Apple 平台侧官方值：iOS/iPadOS 默认控件 **44×44 pt**，最低 **28×28 pt**；控件间距约 **12 pt**（带 bezel）/ **24 pt**（无 bezel） | [WCAG 2.2 §2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum) ｜ [Apple HIG – Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility) |

### 3.2 `viewport-fit=cover` 与 `env(safe-area-inset-*)` 的官方定义

Apple / WebKit 官方原文（iPhone X 时代的官方说明，仍是 `viewport-fit` 与 `env(safe-area-inset-*)` 的一手出处）：

> The first new feature is an extension to the existing viewport meta tag called `viewport-fit`, which provides control over the insetting behavior. `viewport-fit` is available in iOS 11. The **default value of `viewport-fit` is `auto`**, which results in the automatic insetting behavior… In order to disable that behavior and cause the page to lay out to the full size of the screen, you can set `viewport-fit` to `cover`.
>
> To achieve this, WebKit in iOS 11 includes a new CSS function, `env()`, and a set of four pre-defined environment variables, `safe-area-inset-left`, `safe-area-inset-right`, `safe-area-inset-top`, and `safe-area-inset-bottom`.
>
> The `env()` function shipped in iOS 11 with the name `constant()`. Beginning with Safari Technology Preview 41 and the iOS 11.2 beta, `constant()` has been removed and replaced with `env()`. … For browsers that do not support `env()`, the style rule that includes it will be ignored; for this reason, it is important to continue to separately specify **fallback rules** for any declarations using `env()`.

来源：[WebKit — Designing Websites for iPhone X（2017-09-22，安全区部分 2017-10-31 更新）](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)

官方给出的「安全区 + 普通间距」合并写法与理由：

> To solve this, we want to specify that our padding should be the default padding or the safe area inset, whichever is greater. This can be achieved with the brand-new CSS functions `min()` and `max()` … It is important to use `@supports` to feature-detect `min` and `max`, because they are not supported everywhere, and due to CSS's treatment of invalid variables, to not specify a variable inside your `@supports` query.

来源：同上

**规范地位标注**：CSS Viewport Module Level 1（Editor's Draft, 29 August 2026）的 §3.1「Properties」明确列出 viewport meta 的 recognized properties 为 `width`、`height`、`initial-scale`、`minimum-scale`、`maximum-scale`、`user-scalable`、`interactive-widget`——**不含 `viewport-fit`**；`viewport-fit` 在 W3C 侧**未找到官方依据**，其唯一权威定义来源是 Apple / WebKit 官方文档。来源：[CSS Viewport Module L1 §3.1](https://drafts.csswg.org/css-viewport-1/#viewport-meta-element)

### 3.3 地址栏导致的 viewport 高度变化 —— `100vh` vs `100dvh`

规范层面（CSS Values and Units Module Level 4 §6.1.2.1，**Working Draft, 12 March 2024**）：

> **large viewport** — The large viewport-percentage units (`lv*`) and **default** viewport-percentage units (`v*`) are defined with respect to the large viewport size: *the viewport sized assuming any UA interfaces that are dynamically expanded and retracted to be retracted*. … when these retractable elements are shown, they can obscure content that is sized or positioned using these units.
>
> **small viewport** — The small viewport-percentage units (`sv*`) are defined with respect to the small viewport size: *the viewport sized assuming any UA interfaces that are dynamically expanded and retracted to be expanded*. … The small viewport-percentage units units are thus "safer" in general, but might not produce the most attractive layout once the user starts interacting with the page.
>
> **dynamic viewport** — The dynamic viewport-percentage units (`dv*`) are defined with respect to the dynamic viewport size: *the viewport sized with dynamic consideration of any UA interfaces that are dynamically expanded and retracted*. … The sizes of the dynamic viewport-percentage units are not stable even while the viewport itself is unchanged.

来源：[CSS Values and Units L4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)

同一规范的附注说明「无前缀单位为什么等同于 large」：

> The original (unprefixed) viewport units were defined relative to the initial containing block … The dynamism of browser chrome shifting in and out during scrolling was invented later, and following Safari's lead, most UAs mapped these units to the larger size. … at this point the mapping to the large viewport-percentage units is presumed to be required for Web compatibility.

来源：[CSS Values and Units L4 §6.1.2.2 注记](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)

厂商官方说明（Google / Chrome 团队，web.dev）：

> While the existing units work well on desktop, it's a different story on mobile devices. There, the viewport size is influenced by the presence or absence of dynamic toolbars. These are user interfaces such as address bars and tab bars. Although the viewport size can change, the `vw` and `vh` sizes do not. As a result, elements sized to be `100vh` tall will **bleed out of the viewport**. … `100vh` on mobile is "correct" when the User-Agent user interfaces are retracted.
> - Large viewport: The viewport sized assuming any UA interfaces that are dynamically expanded and retracted to be retracted.
> - Small Viewport: The viewport sized assuming any UA interfaces that are dynamically expanded and retracted to be expanded.
> - Units representing the large viewport have the `lv` prefix… the small viewport have the `sv` prefix… Its accompanied units have the `dv` prefix: `dvw, dvh, dvi, dvb, dvmin, dvmax`. **Their sizes are clamped between their `lv*` and `sv*` counterparts.**
> These units ship in Chrome 108, joining Safari and Firefox which already have support.
> Note: The values for the dynamic viewport do not update at 60fps. In all browsers updating is throttled as the UA UI expands or retracts.

来源：[web.dev — The large, small, and dynamic viewport units](https://web.dev/blog/viewport-units)

**可直接落地的推论**：iPhone 竖屏 375px 宽的作答页若使用 `100vh` 做满高容器，首屏加载时地址栏展开 → 内容被推出视口；`100dvh` 会跟随工具栏变化但会在滚动中引起重排；`100svh` 保证不被遮挡但会留白。

### 3.4 触控目标尺寸的移动端官方出处

- **W3C 已覆盖**：WCAG 2.2 §2.5.8 Target Size (Minimum, AA) = **24 × 24 CSS px**；§2.5.5 Target Size (Enhanced, AAA) = **44 × 44 CSS px**。来源：[§2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum) ｜ [§2.5.5](https://www.w3.org/TR/WCAG22/#target-size-enhanced)
- **Apple 平台官方值**（HIG「Accessibility」→ Mobility）：默认控件尺寸 iOS/iPadOS **44×44 pt**，最低 **28×28 pt**；控件间距建议带 bezel 约 **12 pt**、无 bezel 约 **24 pt**。来源：[Apple Human Interface Guidelines – Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- 说明：HIG 是 Apple 平台的原生 App 指南，对 Web 内容不具规范强制力，但在 iOS Safari 上是同平台交互的官方参考；**W3C 侧没有 44px 的 Web 强制值**（44px 仅为 AAA 级 2.5.5）。

## 4. 对本工具的直接约束（只写约束事实与阈值）

### 4.1 无障碍约束

1. 所有正文文本与其背景对比度 ≥ **4.5:1**；≥ 18pt（或 14pt bold、CJK 等效）的文本 ≥ **3:1**；判定用未舍入值（4.499:1 不达标）。〔[§1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum)〕
2. 雷达图/条形图中**承载信息的**线、网格线、扇区边界、条形填充与其相邻色对比度 ≥ **3:1**（未舍入；2.999:1 不达标）；纯装饰图形不受限。〔[§1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast)〕
3. 图表若用**颜色**区分维度，必须同时存在**非颜色**等价编码（数值标签 / 表格 / 纹理 / 线型）。〔[§1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast)〕
4. 所有可点击目标（题号面板圆点、选项、上一题/下一题按钮）必须能容纳一个轴对齐的 **24×24 CSS px** 实心方块；不足时须满足「24px 直径圆不相交」的间距例外。〔[§2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum)〕
5. 重要控件（下一题、提交、打印）建议按 **44×44 CSS px**（2.5.5, AAA）设计。〔[§2.5.5](https://www.w3.org/TR/WCAG22/#target-size-enhanced)〕
6. 焦点指示器必须可见（2.4.7）；sticky 头部 / sticky 底栏**不得完全遮住**获得焦点的组件（2.4.11 AA），建议按「任何部分都不被遮住」（2.4.12 AAA）设计；用 `scroll-padding` 为 sticky 头部预留空间。〔[Understanding 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)〕
7. 焦点指示器本身与其相邻底色对比度 ≥ **3:1**。〔[Understanding 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)〕
8. 切题时若移动焦点，焦点顺序须与阅读顺序一致（2.4.3）；焦点样式不得触发翻页（3.2.1）。〔[§2.4.3](https://www.w3.org/TR/WCAG22/#focus-order)｜[§3.2.1](https://www.w3.org/TR/WCAG22/#on-focus)〕
9. **「下一题」置灰方案**：置灰本身不违规，但必答缺失已被定义为 input error，因此必须在页面上给出**文本**错误描述并指明出错题号（3.3.1），有已知修正方式时须给出建议（3.3.3）；错误文本必须独立于按钮的 disabled 状态存在。〔[Understanding 3.3.1](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)｜[§3.3.3](https://www.w3.org/TR/WCAG22/#error-suggestion)〕
10. 单选后**不得自动翻页**，除非事先告知用户（3.2.2）。〔[§3.2.2](https://www.w3.org/TR/WCAG22/#on-input)〕
11. 同一测评流程内已填过的信息（姓名、身份信息、联系方式）须**自动填充**或**可选择**（3.3.7）；浏览器的自动填充不算数；不要求跨会话保存。〔[§3.3.7](https://www.w3.org/TR/WCAG22/#redundant-entry)｜[Understanding 3.3.7](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html)〕
12. 状态消息（进度百分比、已答题数、必答校验结果、模块切换提示）必须可程序化确定且**不依赖移动焦点**即可呈现（4.1.3）；但**模块/tab 切换本身**因属「上下文变化」或「用户交互导致的内容显隐」，**不要求** live region；错误类状态用 `role="alert"`、一般状态用 `role="status"`（官方技术条目 ARIA19 / ARIA22）。〔[§4.1.3](https://www.w3.org/TR/WCAG22/#status-messages)｜[Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)〕
13. 身份证明文脱敏后的残值仍属文本，须满足 §1.4.3；脱敏不得引入低于 4.5:1 的对比。〔[§1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum)〕

### 4.2 打印归档约束

14. `@page` 只用**已跨浏览器实现**的描述符：`margin`（及 `margin-top/right/bottom/left`）与 `size`（含 `portrait`/`landscape`/纸张名）。〔[§4.1](https://www.w3.org/TR/css-page-3/#at-page-rule)｜[§7.1](https://www.w3.org/TR/css-page-3/#page-size-prop)｜[BCD](https://github.com/mdn/browser-compat-data/blob/main/css/at-rules/page.json)〕
15. **页码 / 页眉页脚不得依赖 `@page` margin box**：`@top-center` / `@bottom-center` 等 16 个 margin box 仅 Chrome ≥ 131 支持，**Firefox 与 Safari 至今不支持**。〔[CSS Paged Media §5](https://www.w3.org/TR/css-page-3/#page-margin-boxes)｜[BCD](https://github.com/mdn/browser-compat-data/blob/main/css/at-rules/page.json)〕
16. 需要「共 N 页」时，`counter(pages)` 在规范里存在且恒为总页数，但同样只在 margin box 上下文可用 → 实际不可跨浏览器依赖。〔[§6.1](https://www.w3.org/TR/css-page-3/#page-based-counters)〕
17. 分页保护用 `break-inside: avoid`（图表、评分卡片、汇总表不跨页切断）与 `break-before: page`（强制另起一页）——两者在 Chrome 50+ / Edge 12+ / Firefox 65+ / Safari 10+ 均支持。〔[§3.1](https://www.w3.org/TR/css-break-3/#break-before-break-after-properties)｜[§3.2](https://www.w3.org/TR/css-break-3/#break-inside-property)｜[BCD](https://github.com/mdn/browser-compat-data/blob/main/css/properties/break-inside.json)〕
18. `orphans` / `widows` **在 Firefox 上不生效**，不得作为「段落/表格不被切断」的唯一手段。〔[BCD orphans](https://github.com/mdn/browser-compat-data/blob/main/css/properties/orphans.json)｜[BCD widows](https://github.com/mdn/browser-compat-data/blob/main/css/properties/widows.json)〕
19. `break-before: avoid` 在 Safari 不支持；`recto` / `verso` 在 Safari 与 Firefox 均不支持 → 不用这些值控制单双页起始。〔[BCD break-before](https://github.com/mdn/browser-compat-data/blob/main/css/properties/break-before.json)〕
20. 背景色/图形不靠 `print-color-adjust` 兜底：它初始值就是 `economy`，规范允许 UA「ignore any backgrounds」，且 `exact` 只是 **hint**，用户偏好优先。〔[§4.1](https://www.w3.org/TR/css-color-adjust-1/#print-color-adjust)〕
21. `<body>` 上的背景在 **Chrome 与 Safari 均不打印**（即使 `print-color-adjust: exact` 设在 body 上，也只作用于其后代）→ 报告页底色、卡片底色必须由后代元素自身提供背景，而不是依赖 body。〔[BCD print-color-adjust](https://github.com/mdn/browser-compat-data/blob/main/css/properties/print-color-adjust.json)〕
22. `print-color-adjust` 在 Chrome 需 **136+** 才支持无前缀写法（此前为 `-webkit-print-color-adjust`，Chrome 17+）；Safari 无前缀 15.4+（前缀 6+）；Firefox 97+（另有 `color-adjust` 别名自 48）。〔同上〕
23. `color-adjust` 简写已被规范标为 **deprecated**，应使用更具体的 `print-color-adjust`。〔[§4.2](https://www.w3.org/TR/css-color-adjust-1/#color-adjust)〕
24. 打印时**禁止**在 `@page` 上下文使用 `vh/vw/vmin/vmax`；viewport-percentage 长度在 paged media 中以 **page area** 为基准，与屏幕视口无关。〔[CSS Values 4 §6.1.2](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)｜[MDN @page](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@page)〕
25. SVG 雷达图在打印时必须有**确定的内在尺寸**（`width` + `height` 绝对单位，配合 `viewBox`）；只给 `viewBox` 时 `width/height` 的 used value 为 `auto`，而 `auto` 与百分比**不得**用于推导内在宽高 → 无内在宽高比时按 CSS Images 3 Default Sizing Algorithm 落到默认对象尺寸，会变形。〔[SVG 2 §8.12](https://www.w3.org/TR/SVG2/coords.html#SizingSVGInCSS)〕
26. 图表在纸张上的物理尺寸用 `mm` / `cm` 等绝对单位确定，并配合 `break-inside: avoid` 保证不跨页。〔[§3.2](https://www.w3.org/TR/css-break-3/#break-inside-property)〕
27. 打印样式须保证文字/图表在**白底**上仍可读：UA 可能把浅色字改成深色并忽略深底（economy 行为），因此打印样式表不能依赖「深色背景 + 浅色文字」这一组合传达信息。〔[§4.1](https://www.w3.org/TR/css-color-adjust-1/#print-color-adjust)｜[Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)〕

### 4.3 移动端视口约束

28. 采用 `viewport-fit=cover` 时，页面**必须**用 `env(safe-area-inset-top/right/bottom/left)` 避让刘海、圆角与 Home 指示条；四个变量缺一不可。〔[WebKit 官方博客](https://webkit.org/blog/7929/designing-websites-for-iphone-x/)〕
29. `env()` 不可用的浏览器会**丢弃**包含 `env()` 的那一条声明 → 任何用到 `env()` 的属性都必须另写一条不含 `env()` 的 fallback 声明。〔同上〕
30. `env()` 的旧名 `constant()` 已在 Safari TP 41 / iOS 11.2 beta 被**移除**；如需兼容，只能作为历史事实记录。〔同上〕
31. 安全区内边距与设计内边距取**较大者**（官方用 `max()`），并用 `@supports` 做特性检测；`@supports` 查询中**不得**出现 `env()` 变量。〔同上〕
32. 满高容器不使用 `100vh`（移动端会溢出视口）；优先 `100dvh`（跟随工具栏，但滚动中会重排），关键内容改用 `100svh` 保证不被遮挡。〔[web.dev](https://web.dev/blog/viewport-units)｜[CSS Values 4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)〕
33. `100dvh` 的更新在所有浏览器都被节流，**不是** 60fps 实时；不要把布局稳定性寄托在逐帧重算上。〔[web.dev](https://web.dev/blog/viewport-units)｜[CSS Values 4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)〕
34. `dvh`/`svh`/`lvh` 至少需 Chrome 108+；Safari 与 Firefox 更早支持。〔[web.dev](https://web.dev/blog/viewport-units)〕
35. 无前缀 `vh` 等同 **large viewport**，在工具栏展开时内容可能被 UI 遮住——移动端不要把「无前缀 vh」当作安全高度。〔[CSS Values 4 §6.1.2.1](https://www.w3.org/TR/css-values-4/#viewport-relative-lengths)〕

| `env(safe-area-inset-*)` 的 W3C 规范定义 | **未找到官方依据** | CSS Values 4 正文未出现 `safe-area-inset`；环境变量清单来自 Apple/WebKit 官方文档与 MDN browser-compat-data 的 `safe-area-inset-*` 条目。[Apple 文档](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) ｜ [BCD env.json](https://github.com/mdn/browser-compat-data/blob/main/css/types/env.json) |
| 「打印时 SVG 雷达图变形」的唯一规范成因 | **部分未找到官方依据** | 规范能确定的是两条：paged media 下 viewport-percentage 以 page area 为基准（CSS Values 4 §6.1.2）；`auto`/百分比不得推导 SVG 内在宽高（SVG 2 §8.12）。「SVG 在打印时因缺内在尺寸而变形」的完整机制散落在 CSS Images 3 Default Sizing Algorithm 与 CSS Sizing，本轮**未逐条核实**，只采信上述两条可点名的规范事实。 |
| 打印时浏览器是否保留 SVG `fill` / `stroke` | **未找到官方依据** | MDN browser-compat-data 未收录「打印时 SVG 填充色是否保留」这一行为；`print-color-adjust` 的规范文本只规定背景与文字色的处理，未专门规定 SVG 前景填充。**不得**假设 `print-color-adjust: exact` 就能保住 SVG 配色。 |
| Chrome / Safari 打印预览中「背景图形」开关对 SVG 的影响 | **未找到官方依据** | 该开关属 UA UI 行为，无 W3C 规范定义；仅在 MDN BCD 的 notes 中记录了 `<body>` 背景不打印这一条。 |
| `env(safe-area-inset-*)` 在 Android Chrome 上恒为 0 | **未找到官方依据** | 未找到 W3C 或 Google 官方文档作出该断言；本文件不作此结论。 |

## 一、结论先行（5 条）

1. **底座比旧认知大得多，也比专家团队需要的完整度低得多**：PG 实有 **111 张基表 + 18 视图**（`hr_*` 46 表 / `wx_*` 6 表 / `sal_*` 4 表），而 `data/hr_registry.json` 只登记 **46 个对象 + 24 条口径 + 4 条剔除**（`hr_registry.json:5-633, 634-756, 757-762`）。**登记 ≠ 可用**：数据源侧只接通了企业后台 39 张表 + 企微 6 张表，**企微审批/汇报/日程/客户联系/直播全部未授权**。
2. **「数据链」完整，「分析—汇报」半自动，「做图—面板」基本在数据底座之外**。入库/维护/分析三段已闭环；汇报只有**单发个人**一个出口；做图与面板共 **6 套彼此独立的产物**，生成器散落在 50 个脚本 + `~/.workbuddy/tmp/handover/` 临时目录，**6 级下钻看板与排行榜完全不在 PG 体系内、未登记数据字典**。
3. **群聊通道已经在跑，但走的是「裸 SQL」而非 hr-mcp 的 14 工具**。`wecom_bot_messages` 今天已有 5 条群问答（2026-10-26 10:11–11:07），工具轨迹全是 `mcp__hrq-pg__query_sql` + `bash`；云端 `hr-mcp` 的 14 个固化工具**只写在 `~/.dsh/im/AGENTS.md:57-61` 里当文档**，没有被挂成群机器人可调的 toolset。**这是「专家团队」最该先补的接缝。**
4. **口径纪律已固化成机器可执行的闸门，但 schema 无版本控制**。新鲜度台账 v2、修改留痕、人工定稿表都在跑（`hr_data_revision` 40 行、`hr_data_freshness_v2` 10 条、`hr_roster_confirmed_active` 1 行），**但 `v_active_verified` / `v_data_freshness` / `hr_data_revision` 等核心视图的 DDL 不在 `cloudbase/migrations/` 的 11 个 .sql 里**——只在 PG 里手工建、代码里引用，schema 漂移无保护。
5. **「应该接但没接」的高价值项只有一个：企微审批（`oa/*` 返回 301055）**。请假/加班/出差/报销是 HR 数据里唯一「流程事实」类数据源，后台其他模块已基本探到底。

### 5.2 analyze 的 5 个维度（`hr-mcp/index.py:303-386`）

1. 人员变动（`:311-321`）— 近 N 天 `hr_change_log` 分类计数
2. 离职集中度（`:323-336`）— 单一机构占比 **≥50% 且 ≥2 人** 才判「集中」
3. 职级结构（`:338-364`）— 按 `levelStr` 拆 M/P/O 三序列，并显式警告「中文 levelName 的『专业X级』同时覆盖 P 与 O，不可直接当专业序列用」
4. 储备敞口（`:366-376`）— 在职/待招/在职津贴月合计
5. 制度与名单一致性（`:378-385`）— 制度/公告当日更新 + 企微已无 + 待归类

每维固定输出「结论 + 依据数字 + 建议动作」，归因只写结构性因素（`:288-301`）。

### 5.3 hr-agent-run（自建云端 Agent 运行器）

- **为什么自建**：CloudBase 托管 Agent（OAK）始终 "Agent run failed"，逐层排除后结论是内部异常被吞（`~/.dsh/AGENTS.md:540-560`；`hr-agent-run/index.py:2-11`）。
- **实现**：模型直连 AI 网关（Anthropic 协议，`/v1/ai/cloudbase/v1/messages`，Bearer API Key）→ 工具走 MCP JSON-RPC over HTTP 打自己的 hr-mcp → tool_use/tool_result 回灌 → 最多 **10 轮**，超轮强制「不再调工具直接给结论」（`hr-agent-run/index.py:179-209`）。模式 `ask`（问一题）/ `daily`（`:222-264`）。

## 7. 「周计划与最新进展每一天一一对应」的数据冲突（必须拍板）

现表里 **进展是历史累积流水（10/12 – 10/21），周计划是面向未来一周（10/19 – 10/25）**，两者时间上本来就错位：

- 例：#1 销售提点 —— 进展停在 1012，周计划是 1019/1020/1021；周计划的 1019–1021 **当天尚无进展**
- 例：#15 余休调休 —— 进展已有 1020 的记录，而周计划里 1020 还写着「方案提报董事长」

所以「一一对应」有三种互斥读法，必须由你定：

1. **按周滚动**：表里加「周次」维度，行 = 事项 × 分项 × 周次；本周的周计划与本周已产出的进展逐日对齐，下周滚动新增行
2. **计划与实绩分列**：同一行里「周计划」写本周计划、「最新进展」写截至今天的最新一条，两者不强行对齐，靠「进展日期」列看进度差
3. **拆两张子表**：「事项主表」（事项/分项/时间/责任人）＋「进展日志表」（日期/进展/当日计划）

## 9. 能力硬约束（来自 `/research` 一次调研：`docs/research/wecom-smartsheet-layout-capabilities.md`）

一手来源：`wecom-cli smartsheet --doc`（1678 行服务文档）/ `--schema`（26 个方法）/ 本地技能包 `~/.dsh/skills/wecom-unified/references/wecomcli-smartsheet-*.md`。

### 9.1 「避免合并」不是取舍，是唯一路径

智能表格**没有合并单元格这个原语**：`--doc` 全文 `grep -ci merge` = 0、`grep -c 合并` = 0；
而姊妹服务「在线表格」`wecom-cli sheet --doc` 有完整 `merge` 资源（`Sheet_merged_set/get/clear`，支持 all/rows/columns）。
→ 合并属在线表格专属；智能表格只能靠**视图层分组 + 条件填色**制造视觉分段。

### 9.2 记录是扁平 map，没有嵌套子结构

`OaRecord.values: Record<string, string>`——一条记录 = 字段→单值，无子记录、无内嵌明细表。
→ **「一天一条进展」只能是一行记录**；把多天进展拼进一个 text 单元格，就是现在这版表的毛病（等价于合并）。
→ 周计划块「按天逐行、与当天进展 1:1」**强制长表**；宽表方案是「列对列」，天然做不到 1:1，且周数一多字段数暴涨。

### 9.3 改造成本与顺序

| 约束 | 影响 |
|---|---|
| **字段列顺序 = 字段添加顺序，API 无法改写**（`col_infos` 只有 `field_id/field_title/width`，无 order） | 现有子表的 12 列顺序是旧版式；**要按目标版式排列，只能新建子表**（按目标顺序 add 字段），不能原地改 |
| **视图类型创建后不可改**（只能删了重建） | 新建时就要把 grid/gantt/kanban/calendar 的类型一次定对 |
| 单子表 ≤ 20000 行 / ≤ 150 字段；`records add` 单次 ≤ 2000 | 39 事项 × 30 天 ≈ 1170 行，容量无忧 |
| `records list` 要求 `limit × 返回列数 < 10000` | 15 列时单次 ≤ 666 行，需 cursor 翻页（读取侧瓶颈，非存储瓶颈） |
| ViewType 仅 6 种：grid / kanban / gallery / gantt / calendar / form，**无 pivot** | 「六大模块 × 人/流程/成本」的交叉统计**不能靠透视视图**，只能靠 grid 分组 + 公式/图表 |
| 跨子表关联可用 `reference` / `two_way_link_records` / `lookup`（8 种 rollup） | 打开「事项主表 + 进展日志表」双表结构这条路（见 R2-5） |
| 字段类型 27 种；目标列映射：模块/分项 → `text` 或 `single_select`；进展 → `text`；日期 → `date_time`（写入必须 `YYYY-MM-DD HH:mm:ss`）；责任人 → `user`（`[{userName}]`）；负责人类型 → `single_select`；协调事项 → `text` | 责任人可升级为成员字段（可 @、可统计），但多值写法「各机构人力负责人、汪洋」需改口径 |
